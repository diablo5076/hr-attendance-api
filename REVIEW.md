# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 30-34) | Grace period boundary off-by-one: `minutes > 10` returns 0 when late by 10m 1s. Per R2, grace period is 10:00; late minutes are floor from shift start. | Input: shift 09:30, punch-in 09:40:01 IST. Expected: 10 late minutes. Starter returns: 0. | Checked `diff_sec > 600` (strictly more than 10:00), then calculated whole minutes `int(diff_sec // 60)` elapsed from shift start. |
| 2 | `compute_late_minutes` (lines 30-34) | Timezone and overnight shift unawareness: `punch_in.replace(hour=h, minute=m)` mutates naive/UTC time directly. For overnight shifts (e.g. 22:00-06:00) punched at 00:05 IST, it sets start to 22:00 the same day (future), giving 0 late minutes. | Overnight shift 22:00-06:00, punch-in 00:05 IST. Expected: 125 late minutes. Starter returns: 0. | Converted punch-in to IST, resolved the shift's calendar day via `get_attendance_date()` adhering to R1, and computed difference against true shift start instant. |
| 3 | `compute_work_hours` (lines 37-38) | Rounding mode defect: Uses Python's built-in `round(..., 2)` which performs banker's rounding (round-half-to-even) rather than round-half-up (R4). | Duration resulting in 2.675 hours. Python `round(2.675, 2)` gives 2.67; R4 requires 2.68. | Used `Decimal(diff_sec) / Decimal(3600)` with `quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`. |
| 4 | `compute_overtime` (lines 41-43) | Missing 30-minute threshold: Computes overtime without checking whether elapsed minutes >= 30 (R3). | Punch-out 10 or 25 minutes after shift end. Expected: 0 overtime minutes. Starter returns: 10 or 25. | Added threshold check `mins if mins >= 30 else 0`. |
| 5 | `compute_overtime` (lines 41-43) | Overnight shift calendar day defect: `datetime.fromisoformat(date_str).replace(hour=h, minute=m)` places `shift_end` on the attendance date (`date_str`), but for overnight shifts, shift end is on the next calendar day. | Overnight shift 22:00-06:00 on 2026-07-06, punch-out 06:40 IST on 2026-07-07. Starter evaluates `shift_end` as 2026-07-06 06:00 (24h earlier). | Added 1 calendar day to `shift_end_dt` when shift is overnight (`shift_end <= shift_start`). |
| 6 | `GET /health` (lines 65-67) | Missing database health check: Returns 200 unconditionally without pinging MongoDB, violating the contract requirement to return 503 if MongoDB fails to respond. | Stop MongoDB service and call `GET /health`. Starter returns 200; contract specifies 503. | Executed `db.command("ping")` inside a try/except block; raised `HTTPException(503)` on failure. |
| 7 | `POST /employees` (lines 70-77) | Duplicate employee race condition: Checks uniqueness using `find_one` before `insert_one`. Concurrent requests with the same `emp_code` both pass the check. | Two concurrent `POST /employees` requests with identical `emp_code`. Symptom: Duplicate employee records created in database. | Created unique index on `emp_code` at startup and caught `DuplicateKeyError` to return 409. |
| 8 | `POST /employees` (lines 70-77) | Missing validation for shift times and input schema: Does not validate `shift_start != shift_end` (returns 201 instead of 422), and lacks regex validation on `emp_code`, `email`, and `joined_on`. | `POST /employees` with `shift_start: "09:30"`, `shift_end: "09:30"`. Expected: 422 Unprocessable Entity. Starter creates employee. | Added Pydantic field regex validators and an explicit check returning 422 when `shift_start == shift_end`. |
| 9 | `POST /employees` (lines 70-77) | `created_at` timestamp format mismatch: Stores `datetime.now()` (naive local time) and returns datetime string in JSON instead of integer epoch milliseconds. | Inspecting `created_at` in response. OpenAPI requires integer epoch milliseconds (e.g. 1783312500000). | Stored UTC BSON datetime in MongoDB and formatted response with `to_epoch_ms(doc["created_at"])`. |
| 10 | `GET /employees` (lines 80-88) | Pagination off-by-one error: Computes `skip = page * page_size`. For page 1, `skip = 20`, skipping the first page of results entirely. | Request `GET /employees?page=1&page_size=20`. First 20 employees are omitted from the response items. | Fixed skip formula to `(page - 1) * page_size`. |
| 11 | `GET /employees` (lines 80-88) | Total count ignores filter: Calls `db.employees.count_documents({})`, which counts all employees rather than the filtered subset. | Request `GET /employees?department=Engineering` in a DB with 50 employees and 5 in Engineering. Starter returns `total: 50` instead of 5. | Passed filter `q` to `db.employees.count_documents(q)`. |
| 12 | `GET /employees` (lines 80-88) | Missing sorting: Does not sort results by `emp_code` ascending as required by OpenAPI contract. | Querying `/employees` returns documents in natural insertion order rather than sorted by `emp_code`. | Added `.sort([("emp_code", 1)])` to cursor. |
| 13 | `POST /attendance/punch-in` (lines 91-112) | Unhandled missing employee (500 Internal Server Error): When `emp_code` does not exist, `emp` is `None`; `emp["shift_start"]` raises `TypeError` -> 500. | `POST /attendance/punch-in` with `emp_code: "EMP9999"`. Expected: 404. Starter returns: 500. | Added explicit check: `if not emp: raise HTTPException(404, "Employee not found")`. |
| 14 | `POST /attendance/punch-in` (lines 91-112) | Punch-in race condition: Uses check-then-insert (`find_one` then `insert_one`), allowing concurrent punch-ins for the same date to both succeed. | Parallel punch-in requests for same employee and date. Symptom: Multiple punch-in records for one date. | Created unique compound index on `("emp_code", "date")` and handled `DuplicateKeyError` returning 409. |
| 15 | `POST /attendance/punch-in` (lines 91-112) | Local calendar date assignment: Sets `date = ts.date().isoformat()`, ignoring IST timezone and overnight shift business rules (R1). | Overnight shift punch-in at 00:30 IST on 2026-07-07. Starter assigns date `2026-07-07` instead of `2026-07-06`. | Implemented R1 in `get_attendance_date()`, adjusting date back by one day for overnight shifts when punching in before `shift_end`. |
| 16 | `POST /attendance/punch-in` (lines 91-112) | Contract violation on response shape: Adds `doc["id"] = str(res.inserted_id)`. The schema `AttendanceRecord` has no `id` or `_id`. Also accepts invalid `status` values like `ABSENT`. | Sending `status: "INVALID"`. Starter inserts record; contract requires 422. Output contains extraneous `id` field. | Validated `status` enum (`PRESENT`, `WFH`, `ON_DUTY`), omitted internal identifiers, and converted instant timestamps to epoch milliseconds. |
| 17 | `GET /attendance` (lines 115-139) | Full collection in-memory loading (scalability defect): Loads entire collection into Python memory via `list(db.attendance_logs.find(q))` and sorts in memory. | Running on ~100k attendance records causes high memory spike and timeouts. Violates contract constraint. | Delegated sort, skip, limit directly to MongoDB cursor backed by compound index `("date", -1), ("emp_code", 1)`. |
| 18 | `GET /attendance` (lines 115-139) | Missing date range validation and incomplete sort: Does not validate `date_from > date_to` (must return 422), and only sorts by `date` desc without secondary sort on `emp_code` asc. | Request with `date_from=2026-07-10&date_to=2026-07-05`. Expected: 422. Starter executes empty query returning 200. | Added validation `if date_from > date_to: raise HTTPException(422)` and sorted by `[("date", -1), ("emp_code", 1)]`. |

## Items examined and determined NOT to be defects
* **Database fallback configuration (`MONGO_URI`, `MONGO_DB`)**: Providing sensible local default fallbacks while reading from environment variables first allows seamless local testing without compromising production injection.
* **Default shift parameters (`shift_start: "09:30"`, `shift_end: "18:30"`)**: These match the defaults defined in the OpenAPI specification.
* **Use of Pydantic models for request bodies**: Pydantic models align with FastAPI idiomatic practices for request parsing and validation.
